# トラブルシューティング記録

踏んだ不具合と、その特定に使った方法の記録。同じ罠を二度踏まないためのもの。

共通して効いたのは「**その仮説が正しいなら必ず現れる量**を特定して測る」という手順。
症状の一致だけで原因を認めると、たいてい外れる。

## 提出

### 提出物が `Validation Episode failed` で通らない

`main.py` の先頭で `Path(__file__)` を使っていた。**Kaggle は `main.py` をソースとして
読み込んで exec するため、その名前空間に `__file__` が存在しない**。読み込み時点で
`NameError` になり、エピソードが即失敗する。

公式サンプルが最初からこう書いてある理由がこれ。

```python
file_path = "deck.csv"
if not os.path.exists(file_path):
    file_path = "/kaggle_simulations/agent/" + file_path
```

**特定方法**: `kaggle_environments` の `cabt` 環境をローカルで動かすと、そのまま再現する。

```python
from kaggle_environments import make
env = make("cabt", debug=True)
env.run(["/path/to/main.py", "random"])   # first / random がベースライン
```

エンジンはプロセス内シングルトンなので、**1エピソードずつ別プロセスで**回すこと。
同一プロセスで複数回すと状態が壊れて偽の失敗が出る。また `os.chdir()` で展開先を
カレントにしておく(本番の `/kaggle_simulations/agent` 相当)。

### 提出物の形式

成功実績があるのは**単体完結の `main.py`**。`training/` パッケージを同梱して薄い
`main.py` から import する形は通らなかった。`scripts/build_submission.py` は
`src/training/` のモジュールを機械的に連結して1ファイルを生成する
(手でコピーしないので学習側と食い違わない)。

tar のエントリ名にも注意。`tar -czf x.tar.gz -C dir .` は全エントリが `./` 始まりになる。
中身を名前で明示して `./` を付けない。

**提出前に必ず `kaggle_environments` で複数エピソード完走を確認する。**
1日5件の枠を、確認せずに5件とも失敗で使い切ったことがある。

## 学習

### 方策がまったく変化しない

13ラウンド通して `approx_kl=0.0000` / `clip_fraction=0.0000`、エントロピーも動かない。
一方 `value_loss` は下がっており、価値ヘッドだけは学習していた。

原因は埋め込みの初期化を一律 `1/sqrt(d_model)` 倍していたこと。
盤面トークンは数十個の特徴を足すので縮めても生き残るが、**行動トークンは数個しか
足さないので潰れた**(RMS 0.073 対 0.95)。デコーダ層は
`norm1(x + 交差注意(x, 盤面, 盤面))` なので、行動の情報が7%まで薄まって LayerNorm の後に消える。

結果、**行動ごとのスコア差が厳密に 0.0000** になり、softmax は定数の足し算に不変なので
方策が完全な一様分布に固定されていた。`decoder_bag`(全パラメータの40%)への勾配は
`2.7e-07` で、モデルの4割が一度も学習されていなかった。

修正は `EmbeddingBag` の出力に `LayerNorm` をかけるだけ。足し合わせる特徴数に依らず
尺度が揃うので、注意の飽和防止と行動情報の保持を両立できる。

| | 修正前 | 修正後 |
| --- | --- | --- |
| 行動ごとのスコア差 | 0.0000 | 0.1037 |
| `decoder_bag` の勾配 | 2.7e-07 | 2.9e-03 |
| 方策勾配 全体 | 5.6e-05 | 9.7e-02 |

**特定方法**: 方策スコアを「盤面由来」と「行動由来」に分解する。同じ行動群に別の盤面を
与えてスコアが変わらなければ、デコーダは盤面を見ていない。逆に盤面を固定して行動軸方向の
分散を測れば、行動を見ているかが分かる。

### 「両席を同時学習すると勾配が相殺する」という指摘

ゼロ和なので報酬の和が0、よって勾配も相殺する、という指摘を受けた。**成立しない。**

方策勾配は ∇log π(a|s)·A で、席0と席1は別々の観測で別々の行動を選ぶ。
評価点が違うので、報酬の符号が逆でも打ち消し合わない。

```
席0と席1の勾配の cos類似度 = -0.070   (完全相殺なら -1)
合成後のノルム 1.038e-05   (無相関予測 1.074e-05 の 97%)
```

席を分けるとデータが半分になるだけ。ただし指摘された**症状**(方策が凍結している)は
正しかった。原因の説明だけが誤っていた。この2つは分けて扱う。

### MCTSが何ラウンド回しても候補を採用しない

ゲート判定に「評価試合が**全て**完走したときだけ採用する」という条件があり、
32試合中1つでも失敗すると候補を捨てていた。

```
candidate vs current_best: 19勝11敗 (63.3%)  failed: 2
pooled_win_rate=0.627  complete=False  accepted=False
```

**63%勝っていた候補が、2試合の失敗だけで不採用**になり続けていた。
自己対戦側は `min_completion_rate: 0.8` で運用しているのに、ゲートだけ100%を要求していた。
完走率80%基準に緩和済み。

### その他

- **`vs random` が評価指標として無意味** — 最初から100%で飽和し、120ラウンド連続で
  何も判別できなかった。first-index を固定ベースラインにした
- **1ラウンド12戦では何も分からない** — 95%信頼区間が±29ポイント。数十ラウンドまとめて集計する
- **デッキ抽選が全ラウンドで固定されていた** — seed が `seed + game_index` でラウンド項が無く、
  round 1/2/17 が同一の対戦だった。`seed + round_num * games_per_round` に修正
- **最大HPの取り違え** — 印刷HP(`CardData.hp`)を使っていた。19.7%が実際の最大HP
  (`Pokemon.maxHp`)と食い違い、18.6%はHP比が1.0を超えていた
- **異なる合法手が同一トークンになっていた** — 所有者と領域を入れておらず、
  「自分のベンチのDwebble」と「相手のベンチのDwebble」が区別できなかった(実測105件)
- **テストが空振りしていた** — `battle_start()` 直後はコイントス選択で場が空なので、
  ポケモンが並んだ局面のコードが一度も実行されていなかった。
  わざと off-by-one を入れてもテストが通ることで発覚した

## ハードウェア

### メモリ32KBの不良

学習が突然 round 1 すら越えられなくなった。症状が毎回違う。

```
SIGSEGV (exit -11)
corrupted size vs. prev_size (exit -6)     glibcのヒープ破壊検出
ValueError: Overflow when unpacking long long
JSONDecodeError (204,389文字のうち18,533文字目で切断)
```

決め手は「**入力として存在し得ない値**が出た」こと。インデックスに書くのは高々1万程度の
小さな整数なのに、10進4,300桁の整数が出てきた。書き込まれた後にメモリを踏まれている。
**入力検証では原理的に直らない。**

物理メモリ 14.0 GiB 付近の8ページ(32KB)が、書き込んだ値を保持していなかった。
確保量がそこに届くと必ず踏む。非ECCメモリなのでカーネルは何も記録しない。

`soft_offline_page` でそのページを退避して解決した。BIOSでXMPが無いことを確認して
設定起因を否定し、物理アドレスを特定して隔離、systemdで恒久化するまでの全手順と
実際の出力は [memory-fault/README.md](memory-fault/README.md) にある。

**教訓**: 「コードを変えていないのに突然壊れ始めた」「壊れ方が毎回違う」の2つが揃ったら、
ハードウェアを疑う。非ECCなら記録が残らないので、自分で測るしかない。

### サーマルスロットリング

CPUが100℃に達すると `intel_powerclamp` が緊急冷却に入り、`max_perf_pct` が17まで下がる。
性能が6分の1になるため試合がタイムアウトし、大量の失敗試合が出る。

`idle_inject` というカーネルスレッドが十数本、各50%のCPUを使っているように見えるが、
これは**原因ではなく100℃への反応**。CPUを強制的にアイドルにして冷やしている。

RAPL(`/sys/class/powercap/`)からの電力制限は、多くのコンシューマ向けボードで
ファームウェアにロックされていて効かない。書き込みは成功したように見えて、
読み戻すと `0` になる。**OSから制御できないので、BIOS で設定するかワーカー数で調整する。**

無負荷で80℃を超えるなら冷却の故障。ケース内温度(`SYSTIN`)やNVMe温度が正常なのに
CPUだけ高い場合、熱がヒートシンクまで届いていない(簡易水冷のポンプ停止、
空冷の接触不良・目詰まり)。

```bash
sudo modprobe nct6775 && sensors    # ファン/ポンプの回転数
```

### メモリ関連で起動不能にした

`memmap=` を GRUB に書いて起動しなくなった。`/etc/default/grub` はシェルが読むので
`\$` でエスケープするが、**GRUB自身も `$` を変数として解釈する**ため、
そこでも消えてカーネルには `memmap=1M` だけが渡る。これは「メモリを1MBだけ使う」という
全く別の意味になる。

エスケープを二重にする(`\\\$`)か、**`memmap=` を使わず systemd で
`soft_offline_page` を起動時に実行する**。後者は失敗しても起動に影響しないので安全。

復旧は GRUB メニュー(Shift 押しっぱなし / Esc 連打)で `e` を押し、
`memmap=` を削除して Ctrl+X。**画面が必要なので、遠隔のみの状況では復旧できない。**
`memmap=` を投入する再起動は、物理アクセスできるときに行うこと。

## 測定でやりがちな失敗

- **測定行為が測定対象を汚染する** — 学習中に診断スクリプトを並行実行してCPUを奪い、
  「1ラウンド220秒」と誤って報告した。実際は68秒だった
- **ログの末尾だけを見る** — 「エントロピーが下がっていない」と判断したが、
  系列で見れば単調に下がっていた
- **エポックを揃えずに比較する** — `value_loss` は同じラウンド内でも epoch 1 と 4 で違う。
  early stopping で回るエポック数が変わるので、ログ末尾の値は比較にならない。epoch 1 で揃える
- **自明に成立するテストを書く** — `role * count // count == role` のような、
  何も検証していないテストを書いていた。わざと壊して落ちることを確認する
