# 自己対戦MCTSをマルチプロセス化しようとしたら、次々に謎のクラッシュが出て原因調査に追われた話

## はじめに

対戦ゲームのAIエージェントを、AlphaZero的な自己対戦MCTS(モンテカルロ木探索)で学習させるプロジェクトに取り組んでいる。対戦エンジンは配布されたバイナリ(共有ライブラリ)をPythonからctypes経由で呼び出す形で、GPUには対応しておらずCPUだけで動く。しかもこのエンジンはプロセスグローバルな状態を持つ作りで、対局ごとのセッションハンドルが無いため、**1つのプロセスの中で複数の対局を同時に進めることができない**。

自己対戦でまとまった量の学習データを集めるには、1手ごとに数十回の探索(そのたびにニューラルネットの評価が走る)を伴うMCTSを1ラウンドあたり200局ほど回す必要がある。1局ずつ順番にやっていては到底終わらないので、「複数のプロセスに対局を分担させて並列化する」という、ごく普通の方針を取った。ところが、この並列化がとにかく一筋縄ではいかず、原因の異なる複数のクラッシュ・フリーズに次々と遭遇することになった。この記事は、その調査の記録である。

構成としては、
1. forkに起因するデッドロック(すぐ解決)
2. 原因不明の完全フリーズ(`ptrace`が使えない環境での調査)
3. クラッシュ症状への変化と、体系的な切り分け
4. 「本当に自分のコードのせいか」を実験で確かめる
5. ロックによる対策とその失敗
6. 撤退の判断

の順に書いていく。

## 1. 最初の問題: forkしたら全プロセスが凍りついた

`multiprocessing.Pool`で対局を並列実行する実装を組んで、いざ本番の学習を回してみたところ、1ラウンド目から一切進捗が出ない状態になった。`uptime`で見る`load average`がほぼ0で、明らかにどのプロセスも計算していない。

`ps aux`で各プロセスの状態を見てみると、全プロセスが`S`(スリープ)状態。さらに`ps -eo pid,stat,wchan`で「何を待っているか」を見ると、メインプロセス・ワーカープロセスともに`futex_wait_queue`。つまりOSレベルのロック(futex)待ちで完全に停止していた。

原因はすぐに見当がついた。Pythonの`multiprocessing`はLinuxではデフォルトで`fork`を使って子プロセスを作る。forkは「その瞬間の親プロセスのメモリ状態をそのままコピーして子プロセスにする」仕組みだが、コピーされるのは**メモリの中身だけ**で、実行中のスレッドはコピーされない(子プロセスはforkを呼んだそのスレッド1本だけを引き継ぐ)。

ここで問題になるのが`torch`だった。`torch`をimportすると、内部でスレッドプール(intra-opの並列化用)を持つ。もしfork した瞬間に、たまたま別スレッドが`torch`内部のロックを保持していたら、そのロックは「保持されたまま」子プロセスにコピーされる。しかし、そのロックを解放するはずだった当のスレッドは子プロセスに存在しない(forkしたスレッドしか残っていない)ので、**そのロックは子プロセスの中で永久に解放されない**。これはPyTorch公式が明言している既知の問題である。

対策は単純で、`multiprocessing.get_context("spawn")`を使い、子プロセスをforkではなく「まっさらな新しいPythonインタプリタを起動する」方式に変えるだけで良い。

```python
# Before (デフォルトのfork、torchインポート後だとデッドロックしうる)
with multiprocessing.Pool(processes=N) as pool:
    ...

# After
with multiprocessing.get_context("spawn").Pool(processes=N) as pool:
    ...
```

spawnはメモリを引き継がないぶん起動が遅く(子プロセスごとに`torch`や依存ライブラリを再importする必要がある)、実際に60局のテストで比較したところforkだとハングしたままだったのに対し、spawnだと全ワーカーがCPU 60〜100%で動き、140.9秒で60局が完了した。速度の代償はあるが、確実性を優先してspawnに切り替えた。

ここまでは、調べればすぐ出てくる典型的なハマりどころだったので、そこまで苦労はしなかった。

## 2. spawnにしたのに、また止まった

spawnに変えて安定した学習が回るようになった、と思っていたところ、しばらく経ってから別の症状に遭遇した。ネットワークの構成(入力特徴量やアーキテクチャ)を変えて改めて学習を回したところ、今度は1ラウンド目の自己対戦(200局)が、25分以上経っても1局も完了しない。以前の実測では200局・並列18プロセスで1ラウンド約690秒(11.5分)だったので、明らかに異常な遅さだった。

`ps`で2回(13分間隔)スナップショットを取って比較すると、メインプロセスも全18ワーカープロセスも、**CPU時間が1秒たりとも増えていない**(例: あるワーカーは2回とも`00:01:37`のまま)。`wchan`もやはり`futex_wait_queue`。今度はspawnに変えたにも関わらず、同じような完全フリーズが起きていた。

ここで困ったのが、原因特定の手段がほとんど封じられていたことだった。`py-spy`や`gdb`、`strace`のようなプロセスにアタッチして調べるツールは、どれも`ptrace`という機能を必要とするが、今使っている実行環境はサンドボックス化されていて`ptrace`が権限で弾かれてしまう(`py-spy dump --pid ...`は`Permission denied`)。

そこで使ったのが、Python標準ライブラリの`faulthandler.dump_traceback_later()`だった。これは外部からアタッチするのではなく、**プロセス自身に、自分の全スレッドのスタックトレースを定期的に吐かせる**仕組みで、`ptrace`を必要としない。

```python
import faulthandler

def _init_worker(...):
    fault_log = open(f"worker_{os.getpid()}_faulthandler.log", "w")
    faulthandler.enable(file=fault_log)
    faulthandler.dump_traceback_later(30, repeat=True, file=fault_log)
    ...
```

各ワーカーの初期化時にこれを仕込んで、30秒おきに専用ファイルへスタックを書き出すようにした上で、もう一度学習を走らせてフリーズの再現を待った。

結果、フリーズしたワーカーのスタックは、

- ニューラルネットのforward計算中(`torch.nn.modules.transformer`の中)
- `torch.no_grad()`コンテキストの終了処理中
- 対戦相手プールのJSON読み込み中(`json.load`)

というように、**バラバラの場所**で止まっていた。1箇所の決め打ちのロックで説明できる話ではなさそうだった。念のためメモリ不足(OOM)による強制終了も疑ったが、`cgroup`の統計を見ると

```
$ cat /sys/fs/cgroup/memory.events
low 0
high 0
max 0
oom 0
oom_kill 0
```

`oom=0 oom_kill=0`で、OOM killもされていないことが確認できた(メモリも23GB以上余裕があった)。

## 3. クラッシュの症状が変わった。体系的に切り分ける

一度プロセスを落として学習を再実行してみたところ、今度はさらに違う症状が出た。フリーズはしていないが、`ps`で見るとワーカープロセスが**次々と死んでは自動的に再起動されている**(10分強で40回以上、本来18プロセスのはずが)。`multiprocessing.Pool`は、ワーカーが異常終了すると自動的に代替のワーカーを立てる仕組みになっているので、パッと見では何ごともなく動いているように見えるが、実際には裏で頻繁にクラッシュしていた。

ここまでいろいろな症状(完全フリーズ、頻発クラッシュ)が出てきて、行き当たりばったりに原因を推測しても埒が明かないと感じたので、一旦立ち止まって、変数を1つずつ切り分ける診断を組むことにした。

### 3.1 単一対局のロジックを疑う

まず疑ったのは「1局分のゲームロジック自体にバグがあるのでは」という可能性。これを検証するため、`Pool`を使わず、`multiprocessing.Process`で1局ずつ独立したプロセスを立てて順番に実行し、終了コード(`process.exitcode`)を記録するだけの診断スクリプトを書いた。`Pool`はワーカーが死んでも自動補充してしまい終了コードが見えなくなる(異常終了したタスクの結果はタイムアウトするまで待たされるだけで、シグナルの種類などは分からない)ので、これを迂回する狙いもあった。

```python
for i in range(20):
    p = ctx.Process(target=play_one_game, args=(i,))
    p.start()
    p.join(timeout=300)
    if p.is_alive():
        p.terminate()
        status = "timeout"
    else:
        status = "ok" if p.exitcode == 0 else f"crash({p.exitcode})"
    print(f"game {i}: {status}")
```

結果、20局を逐次実行して**全て`exitcode=0`(正常終了)**、1局あたり46〜59秒で安定していた。単一の対局ロジックには問題が無いことが分かった。

### 3.2 並列数を段階的に上げる

次に、同じ仕組みを使って、並列数を2→4→8→18と段階的に上げて、同時に複数の対局を走らせる診断に切り替えた(各レベルで2〜3ラウンドずつ試行)。

| 並列数 | 結果(正常/クラッシュ/タイムアウト、複数ラウンド分) |
|---|---|
| 2 | 3/4 正常、クラッシュはSIGSEGV(-11)が1件 |
| 4 | 7/8 正常、クラッシュ1件 |
| 8 | 14/16 正常、クラッシュ2件 |
| 18 | 21/36 正常、**最大78%(14/18)がクラッシュ**したラウンドもあり |

クラッシュコードはほぼ`-11`(SIGSEGV)、まれに`-6`(SIGABRT)。並列数が上がるほどクラッシュ率が急激に悪化しており、これは「一定確率でまれに起きるレースコンディション」というより、**並列数そのものに強く依存するリソース競合**に近い挙動だった。これで「複数のプロセスが同時にエンジンのネイティブ処理を呼ぶこと」自体が問題だと、かなり確度高く言えるようになった。

## 4. それは本当に自分のコードの変更のせいか

この時点で「最近ネットワーク構成や特徴量を変えたから、その変更が悪さをしているのでは」という仮説が浮かんだ。実際、ネットワークの層を1つ増やしたり、疎な特徴量ベクトルの次元を増やしたりしていたので、「1ノードあたりの評価が重くなって、プロセス間のタイミングがずれてクラッシュしやすくなったのでは」という、もっともらしい説明を考えようと思えばいくらでも考えられる状況だった。

しかし、それを裏付ける前に、まず**それが本当かどうかを実験で確かめる**ことにした。もっともらしく聞こえる仮説と、実際に正しい仮説は別物であり、後から検証し直すと前者が的外れだったということはよくある。

`git worktree`を使って、変更を加える前の古いコミット(以前は問題なく学習が完走していたはずのコード)を別ディレクトリにチェックアウトし、全く同じ並列度診断を、同じ環境・同じタイミングでかけ直した。

```bash
git worktree add ../old-version <古いコミットハッシュ>
# 古いコードに対して、3.2と全く同じ並列度診断スクリプトを実行
```

結果:

| 並列数 | 旧コードでの結果 |
|---|---|
| 2 | 4/4 正常 |
| 4 | 8/8 正常 |
| 8 | 13/16 正常(3件クラッシュ) |
| 18 | 15/36 正常、**最大89%(16/18)がクラッシュ**したラウンドもあり |

**古いコード(以前は問題なく動いていたはずのコード)も、今回と同水準、むしろそれ以上の頻度でクラッシュした**。

これで、今回の変更が原因ではなく、**エンジン自体が元々持っていた並列アクセス時の不安定さ**であることがはっきりした。以前たまたま問題なく完走できていたのは、単に運が良かっただけということになる。「なんとなくもっともらしい仮説」を、検証せずに原因と決めつけずに済んだのは良かったと思う。

## 5. ロックで直列化してみる。それでも直らない

原因の見立てがついたところで、対策を考えた。3.1で「単一プロセスなら安全」ということは確認できていたので、理屈の上では、**エンジンへのネイティブ呼び出し部分だけをプロセス間ロックで直列化**すれば、複数プロセスが同時にそこへ触れる状況を無くせるはずだった。ニューラルネットの推論計算(こちらは純粋にPython/torch側の処理で、エンジンには触れない)はロックの外に置き、並列のまま行う設計にした。

```python
_engine_lock = contextlib.nullcontext()  # デフォルトは何もしないダミー

def set_engine_lock(lock):
    global _engine_lock
    _engine_lock = lock

# 対局ループの中で、エンジンのネイティブ関数呼び出しだけを囲む
with _engine_lock:
    obs_dict, start_data = engine.battle_start(deck0, deck1)
...
with _engine_lock:
    next_state = engine.search_step(search_id, action)
```

`multiprocessing.get_context("spawn").Lock()`で作ったロックをワーカー初期化時に配って、これで検証をやり直した。

ところが、これでもクラッシュは収まらなかった。並列8で、ロック無しとほぼ変わらない頻度(3試行で4/8, 3/8, 1/8クラッシュ)で異常終了が続いた。

もう一段深く調べたところ、見落としが見つかった。カード・技のマスタデータを取得する関数が、実は裏でエンジンのネイティブ関数(`AllCard`/`AllAttack`相当)を呼んでいた。この関数は「初回アクセス時だけ結果をキャッシュする」遅延ロード設計になっていて、その初回呼び出しが対局ループの中、**ロックの外側**で行われていた。つまり、直列化したつもりの箇所(`battle_start`や`search_step`)以外にも、複数プロセスが同時にネイティブ処理へ触れる経路が残っていたことになる。

```python
def _init_worker(...):
    with engine_lock:
        # マスタデータの初回ロード(ネイティブ呼び出しを含む)を、
        # 対局ループに入る前にロック内で済ませておく
        card_table()
        attack_table()
    ...
```

ワーカー起動時にこのマスタ情報をロックの内側で先読みしておくよう修正し、再度検証した。

それでも、クラッシュ率はほぼ変わらなかった(並列8で1〜4/8クラッシュのまま)。ロックで塞いだつもりの経路以外にも、まだ見つけられていない競合箇所が残っている可能性が高い。

## 6. 潔く撤退する

ここまで来て、これ以上この不具合を追いかけ続けるのは費用対効果が見合わないと判断した。ブラックボックスのバイナリの内部を手探りで直列化し続けるより、**そもそも並列アクセスをしない**方が確実だと考えたからだ。

最終的に、並列実行を諦めて自己対戦をシングルプロセスに戻すことにした。対局用のプロセス自体は残す(対局用プロセスがクラッシュしても、メインプロセスや保存済みのチェックポイントには影響しないようにするため)が、複数プロセスを同時には走らせない。当然、自己対戦全体のスループットは大きく落ちる(200局が並列時の約11分から、逐次実行だと2〜3時間規模になる)。この先の学習速度をどう確保するかは、また別の切り口(1手ごとの探索を必要としない、より軽量な学習方法への切り替えなど)で考える必要があり、現在検討中である。

なお、この調査の過程で、対局中に例外が発生すると後片付け処理(`battle_finish`相当)が呼ばれずに済んでしまう、という実在のバグも見つかって直すことができた。

```python
# Before: 例外が起きるとbattle_finish()が呼ばれないまま関数を抜けうる
obs_dict, start_data = battle_start(...)
if start_data.errorPlayer >= 0:
    raise ValueError(...)
...
battle_finish()

# After: try/finallyで、必ずbattle_finish()が呼ばれるようにする
obs_dict, start_data = battle_start(...)
try:
    if start_data.errorPlayer >= 0:
        raise ValueError(...)
    ...
finally:
    battle_finish()
```

原因究明そのものは決着しなかったが、副産物として得るものはあった。

## まとめ

今回の一連の調査でやったことを振り返ると、特別なことは何もしていない。

- `ps`でプロセスの状態(`STAT`)を見る
- `wchan`でロック待ちかどうかを疑う
- `cgroup`の`memory.events`でOOMを否定する
- `ptrace`が使えないなら`faulthandler.dump_traceback_later()`で代替する
- `exitcode`を自分で拾える形にして、シグナルの種類(SIGSEGV/SIGABRT/タイムアウト)を区別する
- 並列数のような変数を1つずつ動かして、結果がどう変わるかを見る
- 「もっともらしい仮説」を検証せず原因と決めつけず、`git worktree`で旧コードと実際に比較して確かめる

といった、地道な一つ一つの積み重ねだった。特にすごいツールを使ったわけではなく、標準の`ps`や`multiprocessing`、Python標準ライブラリの`faulthandler`だけで、ここまでの切り分けはできた。

もう一つ、今回の調査で実感したのは「原因を完全に特定できなくても、次に進む判断はできる」ということだった。ブラックボックスのバイナリの内部までは追いきれなかったが、「単一プロセスなら安全」「並列にすると並列数に応じて悪化する」「ロックで塞いだつもりの箇所以外にも競合が残っている」という事実は確立できていたので、それをもとに「これ以上は深追いせず、並列化を諦める」という決断はできた。原因不明のまま無限に粘るのではなく、分かっている事実の範囲で最善の判断をして前に進む、というのも、デバッグの一部なのだと思う。

## 追記: 実は解決した

上記までが「撤退した」時点までの記録だが、後日、次のようなツッコミをもらって調査を再開し、実際に根本原因の一つを特定できた。

> 配布された環境に手を入れていないなら、こちら側の使い方に問題があるのでは。フォーラムに同じ話題が無いのはおかしい。

もっともな指摘だった。改めてSDKのコードを1行ずつ読み直したところ、見落としが見つかった。MCTS探索の1ステップを進める関数は、呼ぶたびにエンジン側に新しい内部状態を確保する仕様になっており、SDKにはそれを明示的に解放するための関数が別途用意されていた。ところが、こちらのコードではその解放関数を**1回も呼んでいなかった**。

MCTSは1手あたり数十回のシミュレーションを行うたびにこの内部状態を新規に確保するので、解放せずに何百局と自己対戦を続けると、解放されないネイティブメモリの割り当てが同一プロセス内にひたすら蓄積していく。これは、

- 単発の対局(使い捨てプロセス)では問題が出にくい
- 対局数・並列度が増えるほど悪化する
- 対局ロジックと無関係な場所でクラッシュする(ヒープが壊れていればどこで表面化してもおかしくない)

という、これまで観測してきた症状すべてと矛盾しない。解放処理を追加したところ、並列度18・3ラウンド連続で完全にクラッシュが消えた(以前は最大78%がクラッシュしていた)。

さらに、ネットワークを構築する処理(内部でカードマスタ取得用の別のネイティブ関数を呼んでいた)の直後に大量のファイル読み込みを行うと、また別の再現性のあるクラッシュが起きることも分かった。今回は幸い、配布物にエンジンのC++ソースコードそのものが同梱されていたため、該当関数の実装を直接読んで確認した。この関数はプロセス生存期間中使い回す静的なバッファを返すだけの安全な実装で、ここにバグは無かった。原因をソースレベルで完全に特定するには至らなかったが、単純に「先にファイル読み込み、後でネットワーク構築」と順序を入れ替えるだけで、この再現条件そのものを回避できた。

振り返ると、「撤退する」という判断自体は間違っていなかったと思っている。あの時点で分かっていた事実からは、それが妥当な結論だった。ただ、「配布物側の問題」と結論づけて終わりにするのではなく、「まず自分たちの使い方を疑う」という視点を後から入れてもらえたことで、実際に直せる問題を見つけられた。ブラックボックスだと決めつける前に、SDKのコードやドキュメント、ソースコードまで一次情報に当たり直す価値は、思っていたよりずっと大きかった。
