# 強化学習が動かなくなった日、原因はメモリの32KBだった

Kaggle のポケモンカードAI対戦コンペに向けて、PPOで方策を学習させている。昨日まで普通に回っていた学習が、今日になって突然 round 1 すら越えられなくなった。コードは1行も変えていない。

そこから丸一日かけて、まったく性質の違う2つのバグを踏み抜くことになった。1つはニューラルネットの初期化に関する自分のミス、もう1つは物理メモリ32KBの不良である。後者に辿り着くまで、私は何度も間違った結論を出した。その過程を残しておく。

## 発端: 方策がまったく学習しない

最初の異常はクラッシュではなかった。学習ログの数値が、13ラウンド通してぴくりとも動かないのだ。

```
epoch 4/4  policy_loss=-0.0000  approx_kl=0.0000  clip_fraction=0.0000  entropy=1.4330
```

PPOの `approx_kl` は「更新前後で方策がどれだけ変わったか」を表す。それが `0.0000` ということは、**方策の出力が一切変化していない**という意味になる。一方で `value_loss` は 0.05 から 0.011 まで下がっており、価値ヘッドはちゃんと学習していた。勾配は流れているのに、方策側だけが止まっている。

1ラウンドあたり53,000サンプルをミニバッチ64で4エポック、つまり約3,300回の勾配更新をしている。13ラウンドで**43,000回更新して方策が動かない**。これは学習率の問題ではない。

### 外部レビューの指摘を検証する

このログを別のAIにレビューさせたところ、こう返ってきた。

> 原因は、同じ共有方策で戦う両席のサンプルを同時にPPO学習していることです。ゼロ和戦なので勝者の報酬 `+1`、敗者の報酬 `-1`、合計は常に `0`。同じパラメータに両方のpolicy gradientを加えると、期待値として相殺されます。

もっともらしい。しかし方策勾配は ∇log π(a|s)·A という形で、**状態 s と行動 a ごとに評価される**。席0と席1は別々の局面で別々の行動を選んでいるので、報酬の符号が逆でも勾配の評価点が違う。相殺するとは思えなかった。

主張された機構が真なら必ず現れる量を測ればいい。席ごとに勾配を計算して、内積を取った。

```
席0の勾配ノルム = 6.298e-06
席1の勾配ノルム = 8.706e-06
cos類似度       = -0.070          (完全相殺なら -1)
合成ノルム      = 1.038e-05       (無相関予測 1.074e-05 の 97%)
```

相殺していない。席を分けても失うのは3%で、代わりにデータが半分になる。AlphaZero も OpenAI Five も同一対局の両席を学習に使っているのだから、当然といえば当然だった。

ただしレビューが指摘した**症状**——方策が凍結している——は正しかった。原因の説明だけが誤っていた。ここは分けて考える必要がある。

### 本当の原因: 行動の情報が潰れていた

方策スコアを分解したら、答えが出た。

```
学習後      行動ごとのスコア差 = 0.0000
ランダム初期化              = 0.0522
```

スコアが盤面だけで決まり、**行動によって一切変わらない**状態になっていた。softmax は全要素に同じ定数を足しても結果が変わらないので、これは厳密な一様分布を意味する。`approx_kl=0` も `clip_fraction=0` もこれで説明がつく。

犯人は、私が数日前に入れた埋め込みの初期化スケーリングだった。

```python
def _scale_embedding_init(self) -> None:
    """埋め込みの初期値を 1/sqrt(d_model) 倍に縮める。"""
    scale = self.d_model**-0.5
    for embedding in (self.encoder_bag, self.decoder_bag, ...):
        embedding.weight.mul_(scale)
```

意図は正しかった。`nn.EmbeddingBag` の既定初期化は `N(0, 1)` で、d_model=128 だと1行のノルムが約11になる。トークンはその和なので、初期状態で注意のlogitが飽和してしまう。だから縮めた。

問題は、**性質の違う2つの埋め込みに同じ係数をかけた**ことだ。

```
encoder_bag 出力 RMS = 0.204  → Transformer通過後 0.95
decoder_bag 出力 RMS = 0.073
```

盤面トークンは数十個の特徴を足すので、縮めても生き残る。しかし行動トークンは数個しか足さない。同じ 0.0884 倍で潰れてしまった。

デコーダ層は `norm1(x + 交差注意(x, 盤面, 盤面))` という構造をしている。行動の素性 `x` が 0.073、盤面由来の交差注意出力が O(1)。**行動の情報が7%まで薄まり、LayerNorm の後に消える**。結果、クエリが行動間でほぼ同一になり、注意重みも出力も同一化した。

`decoder_bag` は全パラメータ 4.22M のうち 1.68M(40%)を占める。そこへ届いていた勾配は `2.7e-07` で、**モデルの4割が一度も学習されていなかった**。

修正は `EmbeddingBag` の出力に `LayerNorm` をかけるだけだった。足し合わせる特徴数に依らず尺度が揃うので、飽和防止と行動情報の保持を両立できる。

| | 修正前(13ラウンド学習後) | 修正後 |
| --- | --- | --- |
| 行動ごとのスコア差 | 0.0000 | 0.1037 |
| `decoder_bag` の勾配 | 2.7e-07 | 2.9e-03 |
| 方策勾配 全体 | 5.6e-05 | 9.7e-02 |
| `approx_kl` | 0.0000 | 0.0100 |
| `clip_fraction` | 0.0000 | 0.1355 |

学習が動き出した。`entropy` が 1.45 から単調に下がり始め、`clip_fraction` も健全な値になった。ここで一件落着——のはずだった。

## 第二幕: 今度は落ちる

学習を再開すると、今度はプロセスごと死ぬようになった。しかも死に方が毎回違う。

```
attempt 1  native crash (exit -11)   SIGSEGV
attempt 2  native crash (exit -11)   SIGSEGV
attempt 3  native crash (exit  -6)   corrupted size vs. prev_size
attempt 4  ValueError: Overflow when unpacking long long
```

3番目は glibc がヒープの管理情報の破壊を検出したときのメッセージだ。4番目は、埋め込みのインデックス列に int64 に収まらない値が混ざっていることを意味する。インデックスの正しい範囲は 0〜7,355 なのに、9,223,372,036,854,775,807 を超える値が入っていた。

さらに遡ると、カードマスタを読む処理で `JSONDecodeError`(204,389文字のうち18,533文字目で切断)も出ていた。

### 「異常な入力」ではなかった

最初、私はこれを入力検証の問題として扱った。エンジンが返す値をそのままインデックスに使っている箇所があるので、そこで範囲チェックをすればいい、と。

検査を入れて動かした。すると検査が発火し、そして**検査自体が落ちた**。

```
ValueError: Exceeds the limit (4300 digits) for integer string conversion
```

壊れた値をエラーメッセージに出そうとして、その数が10進4,300桁を超えていたのだ。

ここで考えを改めた。私たちのコードがインデックスに書く値は、カードIDや領域番号など高々1万程度の小さな整数だけだ。**4,300桁の整数を作る経路は存在しない**。エンジンがどんな値を返そうと、あの数にはならない。

しかも、ワーカーは推論のたびに同じ疎ベクトルを `to_tensors()` に通している。その時点では正常だった。つまり一度は正しく書き込まれた小さな整数が、**書き込まれた後にメモリ上で上書きされた**ということだ。

Python の int は「桁数」と「桁の配列」で表現される。桁数フィールドが踏まれれば、こうなる。

これが決定的だった。**入力検証では原理的に直らない。**検証すべき「不正な入力」が存在しないのだから。私がやっていたのは、壊れた結果を後から見つけて被害を止めるだけの対処療法だった。

## メモリを疑う

「コードを変えていないのに突然頻発するようになった」という事実は、ずっと引っかかっていた。git で確認しても差分は総ラウンド数の1行だけ。同じ seed の同じ試合が、通ったり落ちたりする。壊れ方が毎回違う。

特定のコード経路のバグなら、壊れ方は再現性を持つはずだ。毎回違う場所が壊れるのは、ランダムなメモリ破壊の特徴に見えた。

まず環境を確認した。

```
/sys/devices/system/edac/mc/   → メモリコントローラの登録なし
```

**非ECCメモリ**だった。ECCならビット反転が訂正され、カウンタに記録される。非ECCでは**検出も記録もされず黙って通る**。つまり「カーネルのエラーログが空」であることは、正常である証拠にならない。確認する手段が無いだけだ。

`gcc` は使えたので、メモリテストを書いた。xorshift で疑似乱数列を書き込み、同じ seed から再生成した列と比較するだけの単純なものだ。

```
8スレッド x 900MB x 6パス
完了: 3秒  不一致 1531 件
```

出た。しかも温度は40℃で、熱とは無関係だった。

### 二度の空振り

ここから2回、間違った方向に進んだ。

**1回目**。単一スレッドで4GBをテストすると **0件**。エラーは8スレッド時のみ。「複数コアが同時にメモリ帯域を使うと壊れる」——12世代 Intel + XMP で典型的な症状に見えた。スレッド数の閾値を測った。

```
1スレッド: 0件   2スレッド: 0件   4スレッド: 0件
6スレッド: 1520件   8スレッド: 1532件
```

4と6の間に鋭い境界がある。ワーカーを4に減らせばいい、と結論しかけた。

**2回目**。しかし件数がほぼ一定(約1,530)なのが引っかかった。本物の不安定性ならもっとばらつくはずだ。スレッド数と総メモリ量を分離して測り直した。

```
8スレッド x  100MB (計  800MB)  → 0件
4スレッド x  900MB (計 3600MB)  → 0件
2スレッド x 3600MB (計 7200MB)  → 1531件   ← 2スレッドでも出る
8スレッド x  900MB (計 7200MB)  → 1532件
```

**スレッド数は関係なかった。**同じ7,200MBなら2スレッドでも8スレッドでも同じように壊れる。効いているのは総メモリ量だった。単一スレッドで確保量を変えると、閾値がはっきり出た。

```
4,200MB → 0件
4,800MB → 1529件
```

特定の物理領域が壊れており、確保量がそこに届くと必ず踏む。それだけの話だった。

### 壊れ方の規則性

範囲を詳しく測ると、異様なほど規則的だった。

```
不一致 255〜256件 (1パスあたり)
範囲: 常に 30.0 KB
壊れる位置: 64バイト行の 2番目と4番目 のみ (各128件)
ページ内オフセット: 0x620 で毎回一致
```

しかも1つの `uint64` のうち**1バイトだけ**が、毎回同じ値に置き換わる。

```
run1: 60 → fd    run2: 35 → fd    run3: 01 → fd
run1: 57 → 43    run2: 6a → 43    run3: d7 → 43
```

書いた値が何であれ、読み戻すと同じ値になる。ランダムなビット反転ではなく、その領域が書き込んだ値を保持していない。

## 32KBを切り離す

`/proc/self/pagemap` から物理アドレスを引けるが、これには `CAP_SYS_ADMIN` が要る。コンテナ内で実行するとページ番号が0にマスクされて、ページ内オフセットしか見えない。ホスト側で root として実行した。

```
不一致 256 件
物理アドレス範囲: 0x381270620 〜 0x381277df0
該当ページ: 0x381270000 から 32 KB (8 ページ)
```

`0x381270000` は物理メモリの先頭から約 **14.0 GiB** の位置にあたる。閾値が測るたびに変わったのは、この固定位置に到達するかどうかが、他のプロセスの使用状況で変わるためだった。

Linux には、特定の物理ページをカーネルに使わせなくする仕組みがある。

```bash
for a in 0 1 2 3 4 5 6 7; do
  echo $(printf '0x38127%d000' $a) | sudo tee /sys/devices/system/memory/soft_offline_page
done
```

カーネルがそのページの中身を別の場所へ移し、以後の割り当て対象から外す。再起動は要らない。

```
1スレッド x 7200MB x 6パス
完了: 16秒  不一致 0 件
```

解消した。学習を再開すると、round 11 まで一度もクラッシュせずに到達した。

BIOS を触るには物理アクセスが要る(サーバ向けの IPMI/BMC があれば別だが、コンシューマ向けボードには通常無い)。SSH しか無い状況で解決できたのは幸運だった。

なお `soft_offline_page` は再起動で失われるので、恒久化には GRUB への追記が要る。

```
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash memmap=1M\$0x381200000"
```

`/etc/default/grub` はシェルが読み込むので、`$0` は変数として展開されてしまう。バックスラッシュでのエスケープが必須で、これを忘れると起動しなくなる。実測は32KBだが1MBに丸めているのは、DRAM の不良が行やバンク単位で広がることがあるからだ。32GBのうち1MBを捨てるだけなので、余裕を持たせた方がいい。

## 学習の実態も見えた

騒動のあいだ、私は「モデルを7分の1に縮めたのに学習が遅くなった」と誤った説明を2回した。1ラウンドの内訳を実測して、ようやく正しい数字が出た。

```
自己対戦(300試合, 8並列)  18秒
PPO更新(53,000サンプル)   48秒
評価(12戦)                 2秒
```

以前「220秒」と報告していたのは、**私が診断スクリプトを並行実行してCPUを奪っていた**からだった。測定行為そのものが測定対象を汚染していた。

もう一つ、学習率を 3e-4 から 1e-4 に下げたら1ラウンドが3倍遅くなった件も、理解が浅かった。PPOには `target_kl` による早期停止があり、1ラウンドの方策移動量に上限をかけている。学習率を下げると「同じ上限に到達するまでのミニバッチ数が増える」だけで、上限自体は変わらない。3e-4 では epoch 1 の途中で打ち切られていた更新が、1e-4 では4エポック完走するようになり、処理するミニバッチが約100回から3,312回へ33倍に増えた。**PPO更新のコストを決めるのはモデルサイズではなく勾配ステップ数**だった。

## 振り返って

この一日で、私は少なくとも5回、確信を持って間違った結論を出した。

1. 「両席同時学習で勾配が相殺する」というレビューの機構を、実測せずに否定しかけた(結論は正しかったが、根拠は後から測って得たものだ)
2. 「エントロピーが下がっていない」——ログの末尾数行だけを見ていた。系列で見れば下がっていた
3. 「遅くなったのは学習率のせい」——v1と比べれば自己対戦は速くなっていた
4. 「壊れた値は -1 を符号なしで読んだもの」——実際は4,300桁で、桁数フィールドの破壊だった
5. 「スレッド数が閾値」——総メモリ量だった

共通しているのは、**症状の一致だけで原因を認めてしまった**ことだ。「この仮説が正しいなら必ず現れる量」を特定して測る、という手順を踏んだときだけ、正しい答えが出た。席ごとの勾配の内積、行動軸方向のスコアの分散、スレッド数と総量の分離。どれも測るのは数分で済む。

もう一つは、「異常な入力を検証する」という発想が**そもそも成立しない場合がある**ということだ。入力として存在し得ない値が出てきたなら、それは入力の問題ではない。あの4,300桁の整数を見た時点で気づくべきだった。

非ECCメモリのマシンでは、この種の障害は何の記録も残さずに起きる。ソフトウェアのバグとして何時間も追いかけることになる。ECCの価値は、エラーを訂正することよりも、**「メモリは正常だ」と言い切れること**にあるのかもしれない。

## 付録: 使ったツール

`memtest.c` — 確保量とスレッド数を指定して、書き込みと読み戻しを比較する。

```sh
gcc -O2 -pthread -o memtest memtest.c
./memtest 1 7200        # 1スレッドで7200MB
```

`phys.c` — 不良領域の物理アドレスを特定し、無効化コマンドと GRUB のパラメータを出力する。ホスト側で root として実行する必要がある。

```sh
gcc -O2 -o phys phys.c
sudo ./phys 7200
```

劣化が進行しているなら、時間とともに別の場所にも不良が出る。定期的に流して、新しいアドレスが出てくるようなら交換を検討する、という運用にしている。
