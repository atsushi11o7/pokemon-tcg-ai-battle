# メモリ不良の検証と回避

2026-08-10、PPO学習が round 1 を越えられない状態になった。症状は毎回異なり、
`SIGSEGV`、glibc の `corrupted size vs. prev_size`、10進4,300桁の巨大な整数、
途中で切断された JSON が出た。コードは変更していないのに突然頻発した。

原因はコードではなくメモリの不良だった。ここにあるのは、その特定に使ったツールと手順。

## 分かっていること

```
確保量 4,200MB → 不一致 0件
確保量 4,800MB → 不一致 255件/パス
```

- 約30KBの固定された物理領域が、書き込んだ値を保持しない
- 壊れるのは64バイトのキャッシュライン内の2番目と4番目の位置だけ、毎回同じ
- 1つの `uint64` のうち1バイトだけが、毎回同じ値(`fd`, `43` など)に置き換わる
- 温度67℃・単一スレッドでも発生する。熱も並列処理も無関係
- このマシンは非ECCメモリなので、カーネルはこの種のエラーを検出も記録もしない
  (`/sys/devices/system/edac/mc/` にコントローラが登録されていない)

学習は8ワーカーで約5.4GBを使う(親が試合サンプルで約1.1GB、ワーカーが各約500MB)。
これがちょうど不良領域に届く。ワーカーを4に減らすと約3.5GBに収まる。

## 使い方

### 不良の有無を確認する

```sh
gcc -O2 -pthread -o memtest memtest.c
./memtest 1 7200        # 1スレッドで7200MB
./memtest 1 4200        # 閾値の下なら0件になるはず
```

`不一致 0 件` なら、その確保量では不良領域に触れていない。
BIOS で XMP/EXPO を切り替えた前後で同じ条件を流せば、設定起因かを判別できる。

### 物理アドレスを特定する

**ホスト側で root として**実行する。コンテナ内や一般ユーザでは、`/proc/self/pagemap` の
ページ番号が0にマスクされて物理アドレスが得られない。

```sh
gcc -O2 -o phys phys.c
sudo ./phys 7200
```

そのまま貼れる形で、無効化コマンドと GRUB のパラメータを出力する。

### 回避する

再起動なしで試す(再起動すると元に戻るので、効果確認に使う):

```sh
echo 0x<物理アドレス> | sudo tee /sys/devices/system/memory/soft_offline_page
./memtest 1 7200        # 0件になれば、その領域が原因と確定する
```

恒久化する。`/etc/default/grub` の `GRUB_CMDLINE_LINUX_DEFAULT` に追記して `update-grub`:

```
memmap=<サイズ>K$0x<開始アドレス>
```

`memmap=` の書式を誤ると起動しなくなり得る。遠隔で再起動する前に必ず確認すること。

## 対処の選択肢

BIOS 設定は SSH からは変更できない(OS起動前に動くため)。サーバ向けボードの
IPMI/BMC があれば遠隔で操作できるが、コンシューマ向けボードには通常無い。
`systemctl reboot --firmware-setup` で次回起動時にBIOS画面へ入れるが、
そこから先はメニュー操作なので、画面が無いと操作不能になる。

| 方法 | 遠隔可 | 再起動 | 備考 |
| --- | --- | --- | --- |
| soft_offline_page | 可 | 不要 | 再起動で失われる。効果確認向き |
| `memmap=` + GRUB | 可 | 要 | 恒久的。書式を誤ると起動不能 |
| BIOS で XMP/EXPO 無効化 | 不可 | 要 | 設定起因ならこれで解消する |
| memtest86+ で確定 | 不可 | 要 | モジュールの特定。複数枚なら1枚ずつ切り分け |
| 学習のワーカーを減らす | 可 | 不要 | 確率を下げるだけで保証ではない |
