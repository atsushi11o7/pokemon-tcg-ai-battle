# メモリ不良の特定と隔離

2026-08-10、PPO学習が round 1 を越えられなくなった。コードは変更していない。
原因は物理メモリ32KBの不良だった。特定から隔離までの全手順と、途中で起動不能にした失敗も残す。

## 症状

学習プロセスが毎回違う死に方をする。

```
attempt 1  native crash (exit -11)   SIGSEGV
attempt 2  native crash (exit -11)   SIGSEGV
attempt 3  native crash (exit  -6)   corrupted size vs. prev_size
attempt 4  ValueError: Overflow when unpacking long long
```

3番目は glibc がヒープの管理情報の破壊を検出したときのメッセージ。
別のタイミングでは、カードマスタを読む処理で `JSONDecodeError`
(204,389文字のうち18,533文字目で切断)も出た。

自動再起動(`attempt N/51`)は4回目で「non-retryable exit code 1」と判断して諦めた。

## ソフトウェアではないと判断した根拠

最初は入力検証の問題として扱い、埋め込みインデックスの範囲チェックを入れた。
すると検査が発火し、そして**検査自体が落ちた**。

```
ValueError: Exceeds the limit (4300 digits) for integer string conversion
```

壊れた値をエラーメッセージに出そうとして、その数が10進4,300桁を超えていた。

ここで方針が変わる。インデックスに書くのはカードIDや領域番号など**高々1万程度の小さな整数**で、
4,300桁の整数を作る経路は存在しない。しかもワーカーは推論のたびに同じ疎ベクトルを
`to_tensors()` に通しており、その時点では正常だった。

つまり**一度正しく書き込まれた小さな整数が、後からメモリ上で上書きされた**。
Python の int は「桁数」と「桁の配列」で表現されるので、桁数フィールドが踏まれるとこうなる。

**入力検証では原理的に直らない。**検証すべき「不正な入力」が存在しない。

加えて次の2点が揃っていた。ここでハードウェアを疑うべきだった。

- git で確認してコードは無変更。同じ seed の同じ試合が通ったり落ちたりする
- 壊れ方が毎回違う(特定のコード経路のバグなら再現性を持つはず)

## メモリテストで再現させる

まず環境を確認した。

```sh
ls /sys/devices/system/edac/mc/
# → power  subsystem  uevent    (メモリコントローラの登録なし)
```

**非ECCメモリ**だった。ECCならビット反転が訂正されカウンタに記録されるが、
非ECCでは**検出も記録もされず黙って通る**。「カーネルのエラーログが空」は正常の証拠にならない。

`memtest.c` を書いた。xorshift で疑似乱数列を書き込み、同じ seed から再生成した列と比較するだけ。

```sh
gcc -O2 -pthread -o memtest memtest.c
./memtest 8 900        # 8スレッド x 900MB
# → 完了: 3秒  不一致 1531 件
```

出た。温度は40℃で、熱とは無関係だった。

## 2回の空振り

**1回目。**単一スレッドで4GBをテストすると **0件**。エラーは8スレッド時のみ。
「複数コアが同時にメモリ帯域を使うと壊れる」——12世代Intel + XMP で典型的な症状に見えた。

```
1スレッド: 0件   2スレッド: 0件   4スレッド: 0件
6スレッド: 1520件   8スレッド: 1532件
```

4と6の間に鋭い境界。ワーカーを4に減らせばいい、と結論しかけた。

**2回目。**しかし件数がほぼ一定(約1,530)なのが引っかかった。本物の不安定性ならもっとばらつく。
スレッド数と総メモリ量を分離して測り直した。

```
8スレッド x  100MB (計  800MB)  → 0件
4スレッド x  900MB (計 3600MB)  → 0件
2スレッド x 3600MB (計 7200MB)  → 1531件   ← 2スレッドでも出る
8スレッド x  900MB (計 7200MB)  → 1532件
```

**スレッド数は関係なかった。**効いていたのは総メモリ量。単一スレッドで確保量を変えると、
閾値がはっきり出た。

```
4,200MB → 0件
4,800MB → 1529件
```

特定の物理領域が壊れていて、確保量がそこに届くと必ず踏む。それだけの話だった。

なお閾値は測るたびに変わる(3,000〜4,800MB)。他のプロセスの使用状況で、
その物理ページが割り当てられるかどうかが変わるため。**「使用量を抑える」は回避策にならない。**

### 壊れ方の規則性

```
不一致 255〜256件 (1パスあたり)
範囲: 常に 30.0 KB
壊れる位置: 64バイト行の 2番目と4番目 のみ (各128件)
ページ内オフセット: 0x620 で毎回一致
```

1つの `uint64` のうち**1バイトだけ**が、毎回同じ値に置き換わる。

```
run1: 60 → fd    run2: 35 → fd    run3: 01 → fd
run1: 57 → 43    run2: 6a → 43    run3: d7 → 43
```

書いた値が何であれ、読み戻すと同じ値になる。ランダムなビット反転ではなく、
その領域が書き込んだ値を保持していない。

## BIOSでXMPを確認する

「オーバークロック設定が不安定なだけ」の可能性を潰す。これで直れば何も壊れていないので、
最優先で確認する価値がある。

BIOS へは、キー連打(Del / F2)より確実な方法がある。

```sh
sudo systemctl reboot --firmware-setup
```

**結果**: メモリは Micron製 DDR4-3200 16GB、SPD情報に **JEDEC #1〜#3 のみ表示され、
XMPプロファイルの項目が存在しなかった**。

```
3200 MT/s / 1.20V / CL22-22-22-52    ← JEDEC標準
```

**XMPを使わず定格で動いている。**ASRock B660M Pro RS には `Load XMP Setting` があるが、
そもそもプロファイルが無いので設定項目が出ない。

定格動作で壊れるなら、**メモリモジュール自体(またはメモリコントローラ)の不良**が確定する。
設定で直る種類の問題ではない。

## 物理アドレスを特定する

`/proc/self/pagemap` から物理ページ番号を読む。**ホスト側で root として**実行すること。
コンテナ内や一般ユーザではページ番号が0にマスクされ、ページ内オフセットしか見えない。

```sh
gcc -O2 -o phys phys.c
sudo ./phys 7200
```

```
仮想 0x7df3218b4620 -> 物理 0x381270620
仮想 0x7df3218b4630 -> 物理 0x381270630
...
不一致 254 件
物理アドレス範囲: 0x381270620 〜 0x381277df0
該当ページ: 0x381270000 から 32 KB (8 ページ)
```

`0x381270000` は物理メモリの先頭から約 **14.0 GiB** の位置。
閾値が測るたびに変わったのは、この固定位置に到達するかが他のプロセスの使用状況で変わるため。

**再起動をまたいでも同じアドレス**だった。固定的な物理不良で確定。

```
再起動前: 0x381270620 〜 0x381277df0
再起動後: 0x381270620 〜 0x381277df0
```

## 隔離する

Linux には特定の物理ページを使用対象から外す仕組みがある。**再起動は不要。**

```sh
for a in 0 1 2 3 4 5 6 7; do
  echo $(printf '0x38127%d000' $a) | sudo tee /sys/devices/system/memory/soft_offline_page
done
```

カーネルがそのページの中身を別の場所へ移し、以後の割り当て対象から外す。

```sh
./memtest 1 7200
# → 完了: 16秒  不一致 0 件
```

解消した。学習を再開すると300ラウンド(8.4時間)を**クラッシュ0件**で完走した。

ただし **`soft_offline_page` は再起動で失われる**。恒久化が要る。

## memmap= で起動不能にした話

最初 GRUB の `memmap=` を試して**起動できなくなった**。実家から戻って物理復旧する羽目になった。

原因は**エスケープが二重に必要**だったこと。

`/etc/default/grub` はシェルが読み込むので、`$` を守るには `\$` と書く。
これでシェルは `memmap=1M$0x381200000` という文字列を作る。ところが
**GRUB自身も `$` を変数として解釈する**ため、そこで `$0x381200000` が空に展開され、
カーネルには次だけが渡る。

```
memmap=1M
```

`$` の無い `memmap=1M` は「**メモリを1MBだけ使う**」という全く別の意味になる。起動できない。

### 復旧手順

`GRUB_TIMEOUT=0` かつ `GRUB_TIMEOUT_STYLE=hidden` だとメニューが自動では出ない。

1. 電源投入直後から **Shift 押しっぱなし**(BIOS起動)、または **Esc 連打**(UEFI起動)
2. `Ubuntu` を選んで **`e`**
3. `linux /vmlinuz-...` の行から **`memmap=1M` だけを削除**
4. **Ctrl+X** または **F10** で起動(この変更はメモリ上だけなので次回は元に戻る)

起動したら設定から消す。

```sh
sudo nano /etc/default/grub
# GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"   に戻す
sudo update-grub
sudo grep -c 'memmap' /boot/grub/grub.cfg     # 0 を確認してから再起動
sudo reboot
```

**画面が必要なので、遠隔のみの状況では復旧できない。**
`memmap=` を投入する再起動は、物理アクセスできるときに行うこと。

### どうしても memmap= を使う場合

エスケープを二重にする。

```
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash memmap=1M\\\$0x381200000"
```

`update-grub` 後、`/boot/grub/grub.cfg` に **`memmap=1M\$0x381200000`
(バックスラッシュ付き)** と出ていれば正しい。再起動前に必ず目視確認する。

## 恒久化(systemd)

`memmap=` は使わない。**起動不能のリスクがゼロ**の方法を採る。

```sh
sudo tee /etc/systemd/system/offline-bad-pages.service > /dev/null << 'EOF'
[Unit]
Description=Offline known-bad memory pages at 0x381270000 (8 pages, 32KB)
DefaultDependencies=no
After=sysinit.target
Before=basic.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/bin/sh -c 'for a in 0x381270000 0x381271000 0x381272000 0x381273000 0x381274000 0x381275000 0x381276000 0x381277000; do echo $a > /sys/devices/system/memory/soft_offline_page || true; done'

[Install]
WantedBy=basic.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now offline-bad-pages.service
./memtest 1 7200        # 不一致 0 件を確認
```

`|| true` で失敗を握るので、**サービスが失敗しても起動に影響しない**。
`memmap=` と違って安全に遠隔運用できる。

ただし起動途中の退避なので、既に使われているページは移動できない場合がある
(`Device or resource busy`)。確実性では `memmap=` に劣るので、**再起動のたびに確認する**。

## 運用

学習を始める前のチェックとして習慣化する。

```sh
cd ~/tmp/memory-fault && ./memtest 1 7200
```

`不一致 0 件` なら安全。新しいアドレスで不一致が出るようになったら劣化が進んでいるので、
`sudo ./phys 7200` でアドレスを取り直してサービスを更新し、モジュール交換を検討する。

### RMA

**定格動作(JEDEC DDR4-3200 / 1.20V)での不良なので、明確に保証対象**。
Micron製メモリは通常永久保証で、購入店またはメーカーに交換を請求できる。

複数枚挿している場合、どの1枚かを特定しておくと交換がスムーズ。
1枚ずつ挿して `./memtest 1 7200` を回せば分かる。

```sh
sudo dmidecode -t memory | grep -E "Locator:|Size:|Part Number:|Serial"
```

## ツール

`memtest.c` — 確保量とスレッド数を指定して、書き込みと読み戻しを比較する。`sudo` 不要。

```sh
gcc -O2 -pthread -o memtest memtest.c
./memtest [スレッド数] [1スレッドあたりMB]      # 既定: 1 7200
```

`phys.c` — 不良領域の物理アドレスを特定し、隔離コマンドと GRUB のパラメータを出力する。
**ホスト側で root として**実行する必要がある。

```sh
gcc -O2 -o phys phys.c
sudo ./phys 7200
```

経緯を読み物としてまとめたものは [writeup.md](writeup.md) を参照。
