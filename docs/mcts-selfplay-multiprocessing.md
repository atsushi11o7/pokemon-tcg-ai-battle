# 自己対戦のマルチプロセス化と、`cg`エンジンのクラッシュ調査(解決済み)

`train.py`の自己対戦(self-play)を並列化する際に発生したクラッシュの調査記録。
主要な原因である`SearchState`の解放漏れを特定して修正し、さらにネイティブAPI呼び出し
直後の大量ファイルI/Oで発生する別のクラッシュ条件(こちらはC++内部の根本原因までは
特定できていない)を、呼び出し順序の変更で回避した。いずれも並列実行を維持したまま
対応できた。

## なぜマルチプロセスか

`cg`エンジン(`libcg.so`)はプロセスグローバルな状態を持ち、対局ごとのセッションハンドルが
無いため、1プロセス内で複数対局を同時に進められない([selfplay.py:8-11](../src/training/mcts/selfplay.py#L8-L11))。
また`eval_fn`(ニューラルネット推論)もMCTS探索1ノードにつき1回の未バッチ呼び出しでGPUの
恩恵が薄いため、自己対戦全体をCPUバウンドな複数プロセス並列で実行している。

## 症状

新アーキテクチャ反映後の初回学習で、自己対戦(1ラウンド200試合)が完了しなくなった。
`ps`では全ワーカーが`futex_wait_queue`でCPU時間の増加が止まる完全フリーズと、
ワーカーが頻繁に死んでは自動補充される(`multiprocessing.Pool`の挙動)状態の
2パターンが観測された。

## 切り分け

1. **1局=1プロセスで20局を逐次実行** → 全て`exitcode=0`。単一対局のロジック自体は
   問題無し。
2. **並列度を2/4/8/18と段階的に上げて同時実行** → 並列数に応じてクラッシュ率が悪化
   (level=2で1割程度、level=18で最大78%がSIGSEGV/SIGABRT)。複数プロセスが同時に
   `cg`のネイティブ関数を呼ぶこと自体が原因と判明。
3. **PR適用前の古いコミットをworktreeでチェックアウトし、同じ診断を実施** → 同水準で
   クラッシュ(level=18で最大89%)。**今回の変更が原因ではなく、`cg`エンジン自体が
   元々持っていた不安定さ**と確認(以前の学習は偶然クラッシュを踏まなかっただけ)。
4. **ネイティブ呼び出し部分だけをプロセス間ロックで直列化**(推論計算は並列のまま)
   → 解消せず。ロックで守れていない経路(カード/技マスタ取得の遅延初回ロード)も
   見つけて塞いだが、それでも改善しなかった。

ここで一旦`NUM_SELFPLAY_WORKERS=1`のシングルプロセスに切り替え、根本修正は保留した。

## 原因1: `search_release()`の呼び忘れ

「配布環境ではなくこちら側の使い方の問題では」という指摘を受け、`cg/api.py`を
読み直した。`search_step()`は呼ぶたびに新しい`SearchState`をエンジン側に確保するが、
それを解放する`search_release()`という関数が、コード中どこからも呼ばれていなかった。

MCTSは1手あたり`SEARCH_COUNT`回のシミュレーションのたびに新しい`SearchState`を
作るため、解放しないまま自己対戦を続けるとネイティブメモリの割り当てが同一プロセス内に
蓄積し続ける。これは「対局数・並列度が増えるほど悪化する」「対局と無関係な場所で
クラッシュする(ヒープ破壊の典型症状)」という観測結果と整合する。

`run_mcts`で生成した`searchId`を全て記録し、探索終了時に`search_release()`で
まとめて解放するよう修正([search.py](../src/training/mcts/search.py))。同じ並列度診断で
再検証した結果:

| 並列数 | 修正前 | 修正後 |
|---|---|---|
| 2 | 悪化 | 3/6正常 |
| 8 | 1〜4/8クラッシュ | 23/24正常 |
| 18 | 最大78%クラッシュ | **54/54正常(3ラウンド連続クリーン)** |

これを受けて並列実行を復旧した。

## 原因2: ネイティブ呼び出し直後の大量ファイルI/O

原因1の修正後、200試合規模のテストで別のクラッシュが再発した。切り分けた結果、
`PolicyValueNet`構築(`encoder_size()`/`decoder_size()`経由で`AllCard()`/`AllAttack()`を
呼ぶ)の**直後**に`load_opponent_deck_pool()`(600個超のJSON読み込み)を行うと
確実にSIGSEGVが起きることが判明した。順序を逆にすると発生しない。

配布物には**エンジンのC++ソースコード**(`data/ptcg_engine/`)が同梱されているため、
`AllCard()`/`AllAttack()`の実装を直接確認した。`static`な(プロセス生存期間中使い回す)
バッファを返すだけの実装で、リークする作りにはなっていなかった(原因1とは無関係と判明)。
ソースレベルでの根本原因特定には至らなかったが、`run_training_loop`内の呼び出し順序を
「`load_opponent_deck_pool()`→`PolicyValueNet`構築」に入れ替えることで再現条件を回避した
([train.py](../src/training/mcts/train.py))。修正後、200試合規模の本番相当
テストで199/200正常終了(タイムアウト1件のみ)を確認した。

## 副産物として修正したバグ

調査の過程で、`selfplay.py`の`play_selfplay_game`が`battle_start()`後の例外に対して
`battle_finish()`を呼ばずに抜けうる例外安全性のギャップも見つかり、`try/finally`で
修正した。

## 参考: Kaggleディスカッション

コンペのフォーラムを確認したが、同種のクラッシュに言及した投稿は見つからなかった。
上位勢の多くはGPU上の自己対戦PPOやリプレイからの模倣学習が中心で、生の`cg`エンジンを
CPUマルチプロセスで大量並列実行してMCTS木探索を回す実装をしている参加者自体が
少ない可能性がある。
