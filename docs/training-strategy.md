# 学習方針の記録

Kaggle「The Pokémon Company - PTCG AI Battle Challenge Simulation」向けに、
どういう構成でどう学習させてきたかの記録。判断の理由と、実際に効いたかどうかを残す。

## 全体の構成

盤面から価値を、各行動から方策スコアを出すTransformer1本を、PPOで自己対戦学習させる。
提出時はそのネットワークをDeterminized MCTSでラップして推論する。

```
盤面(疎ベクトル) ──EmbeddingBag──> 26トークン ──TransformerEncoder──> CLSトークン ──> 価値
                                                        │
                                                   (交差注意)
                                                        │
行動群(疎ベクトル) ─EmbeddingBag─> 行動トークン ──DecoderLayer×4──> 方策スコア
```

行動を「固定長の行動空間」ではなく**エンジンが列挙した合法手そのもの**として扱い、
デコーダが盤面へ交差注意して各行動を採点する。合法手の数も種類も局面ごとに変わるため、
固定次元の出力層では表現できない。

## 入力仕様

### v1 → v2 で変えたこと

| | v1 | v2 |
| --- | --- | --- |
| カードIDの持ち方 | `per_role`(出現箇所ごとに独立したカード表) | `shared_card`(同居しない役割は表を共有) |
| D_MODEL | 256 | 128 |
| 層数 | 3+3 | 4+4 |
| パラメータ数 | 28.0M | 4.22M |
| 1手あたり推論(2スレッド) | 3,100ms | 1ms |

`shared_card` にできるのは「同一トークン内で同時に出現しない役割」だけ。`EmbeddingBag` は
sum なので、1トークンに複数のカードが入ると全部足され、どのカードがどの役割だったかの
対応が失われる(役割ベクトルを足しても加算は交換法則が成り立つので結合できない)。

両レイアウトはコード上に残してあり、`model_config.FEATURE_LAYOUT` で切り替える。
テスト(`tests/test_feature_layout.py`)が、トークンごとに書き込む値の多重集合が
両レイアウトで一致することを検証している。片方だけ情報が欠けたら落ちる。

### 盤面(エンコーダ、26トークン / 7,356次元)

- 自分・相手それぞれのアクティブ1 + ベンチ8
- 手札・デッキ・トラッシュ・サイド・スタジアム・LOOKING領域
- ポケモンごとに: カードID、HP(最大/印刷/差分)、付与エネルギーのタイプ別個数、
  特性(skills)、技(attacks)、状態異常、進化段数、このターン出たか
- 自分の60枚デッキの中身(相手には見えない情報を自分だけが持つ)

ベンチのスロット番号はルール上意味を持たないため、位置埋め込みではなく
**所有者(自分/相手/共通) × ゾーン(ベンチ/アクティブ/手札等)** の埋め込みの和で表す。
自分のベンチ8枠は同じ埋め込みを共有する。

### 行動(デコーダ、13,109次元)

選択肢の種類(END/YES/NO/NUMBER/特殊状態/技/カード)ごとにブロックを分け、
対象カードのIDに加えて次を持たせている。

- **所有者と領域** — 「自分のベンチのDwebble」と「相手のベンチのDwebble」を区別するため。
  これが無いと異なる合法手が同一トークンになり、方策は必ず同じスコアを出す
  (実測で105件の衝突があった。現在は0件)
- 技の実効ダメージ(弱点×2・抵抗力−30)、KO可否、相手残りHPに対する割合
- `SelectContext`(何を選ばされているのか)、`contextCard`、`Option.count`

`contextCard` は一度「不要」と判断したが、単一デッキのミラー戦で測ったのが誤りだった。
メタデッキで測り直すと、`effect` から導出できない情報が1.62%あったため追加した。

## PPO の設定と根拠

```yaml
games_per_round: 300      # 1ラウンドあたり約53,000サンプル
rounds: 300
learning_rate: 0.0001
minibatch_size: 64
epochs_per_round: 4
target_kl: 0.02           # 1ラウンドの方策移動量の上限
gamma: 1.0                # 報酬は終局時のみ
gae_lambda: 0.95
entropy_coef: 0.01
eval_games_per_round: 12
workers: 8
```

- **`target_kl` が律速** — 学習率ではなく、これが1ラウンドの移動量を決める。
  学習率を下げると「同じ0.02に到達するまでのミニバッチ数が増える」だけ。
  3e-4 では epoch 1 の途中で打ち切られ、集めたサンプルの4分の1しか使えていなかった
- **KLはミニバッチ16個ごとに確認** — エポック末までまとめて見ていると、
  1エポックで数百〜千stepが走り切ってから止めることになる
- **両席のサンプルを学習に使う** — ゼロ和なので相殺するという指摘を受けたが、
  席ごとの勾配のcos類似度は −0.070(相殺なら −1)で否定された。
  席を分けるとデータが半分になるだけ

## 評価指標

`vs random` は最初から100%で飽和し、120ラウンド連続で何も判別できなかったので廃止した。
現在は **first-index(常に選択肢0を選ぶ)** を固定ベースラインに使っている。
v1の最良の重みでも60.8%しか勝てない、意外に強い相手。

ただし1ラウンド12戦では**95%信頼区間が±29ポイント**あり、単発では傾向を読めない。
判断は必ず数十ラウンドをまとめた集計で行う。

## 結果

### PPO(v2、300ラウンド / 8.4時間)

```
round   1- 60: 40.1%
round  61-120: 64.0%
round 121-180: 70.0%
round 181-240: 70.8%
round 241-300: 68.9%

final.pt vs first-index: 296/400 = 74.0% (95%CI 69.7〜78.3%)
```

round 120 以降はプラトー。**final と round291 の直接対決は 149/300 = 49.7%** で、
最後の9ラウンドは強さに寄与していない。現在の設定でのPPOは収束している。

### 提出履歴(ラダースコア)

| # | 内容 | スコア |
| --- | --- | --- |
| 17 | crustle_team3 + MCTSラップ(探索60/仮説4) | **766.0** |
| 14 | crustle_team3 + 貪欲 | 648.4 |
| 16 | crustle_team3 + 貪欲 | 592.3 |
| 18 | mega_lucario + 貪欲 | 564.1 |
| 15 | crustle_meta + 貪欲 | 566.7 |

**同じ重みでもMCTSでラップするだけで 648 → 766(+118点)。**探索の価値が大きい。
デッキは `crustle_team3` が `crustle_meta` より安定して良い。

## 次の方針

PPOがプラトーに達し、自己教師では頭打ちなので **MCTS学習** へ移る。
探索した訪問回数分布は方策の生出力より必ず良いので、「自分より強い先生」を作れる。

MCTSのゲート判定には、評価32試合が1つでも失敗すると候補を捨てる条件があり、
63%勝っていた候補が不採用になり続けていた。完走率80%基準に緩和済み。

PPOで粘る場合の調整候補:

- `entropy_coef` を 0.01 → 0.003(エントロピーが0.8〜1.1で下げ止まった)
- 試合数を減らしてラウンド数を増やす(集めたサンプルの4分の1しか使っていない)

## 実行

```bash
uv run python -m training.cli train --config configs/ppo_generalist.yaml
uv run python -m training.cli train --config configs/mcts_generalist.yaml
```

設定は `configs/` に2本だけ置く。runごとに `output_dir` へ `run_config.yaml` と
`architecture.yaml` が記録されるので、どの重みがどの構成で学習されたかは後から辿れる。
構造を変えると既存チェックポイントは形状不一致で読めなくなる。

提出物の生成は `scripts/build_submission.py`。詳細は [troubleshooting.md](troubleshooting.md) を参照。
