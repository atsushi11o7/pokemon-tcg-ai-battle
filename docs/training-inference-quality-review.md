# 学習・推論精度レビューと修正報告

## 1. 目的

PTCGエージェントのMCTS/PPO実装を、単に実行できるかではなく、学習時と本番推論時の
整合性、探索の偏り、教師信号、モデル選択の観点からレビューした記録である。

調査日: 2026-08-05

## 2. 重大な問題と修正

### 2.1 MCTS探索中の相手デッキ情報漏洩

修正前の自己対戦では、`search_begin`へ渡す相手の手札・山札・サイドは推測していたが、
ニューラルネット評価関数は探索ノードの手番に応じて自己対戦で実際に使用中のデッキを参照していた。

このため、相手手番の探索ノードでは相手の真の60枚デッキが特徴量へ入り、本番推論では得られない
情報を学習時だけ利用していた。ローカル評価では相手デッキの代わりに自分のデッキを渡しており、
train/inference mismatchにもなっていた。

修正後は、各探索仮説について以下を同時に生成する。

- `search_begin`へ渡す隠れ状態
- その仮説で両プレイヤーが使用しているとみなすフルデッキ

ニューラルネット評価にも仮定デッキを使い、真の相手デッキへアクセスしない。

対象: `src/training/mcts/determinize.py`, `src/training/mcts/selfplay.py`

### 2.2 実在しないカード集合によるdeterminization

修正前は、リプレイ由来のカード頻度プールから各カードを独立に復元抽選していた。
これでは投入上限、進化ライン、デッキ内のカード相関、公開済みカードとの枚数整合性が失われる。
自分側も元の60枚から直接抽選し、手札・場・トラッシュ等を差し引いていなかった。

修正後は次の手順に変更した。

1. 自分の既知デッキから、手札、場、進化元、エネルギー、どうぐ、トラッシュ、
   公開サイド、スタジアムを多重集合として差し引く
2. 相手について、公開カードを必要枚数含む実在デッキ候補だけを抽出する
3. 候補を1つ選び、公開カードを差し引いた残りだけを山札・手札・非公開サイドへ配る
4. 伏せられたアクティブがある場合は、候補デッキの残りに存在するポケモンから選ぶ
5. 公開済みサイドはそのIDを維持し、非公開スロットだけをサンプリングする

整合する候補が存在しない場合は、不正な仮説を黙って生成せず、その試合を説明可能な例外として扱う。

### 2.3 単一仮説への過適合

修正前は1回の意思決定につき隠れ状態を1つだけ作り、全探索予算をその仮説へ投入していた。
偶然選ばれた相手手札・サイドに特化した行動になりやすい。

修正後は既定で5つのdeterminizationへ探索予算を分配し、根の方策分布と価値を加重平均する。
総探索回数は維持するため、計算量の主要部分を増やさずに仮説依存を弱める。
学習時とローカル推論時は同じ集約関数を使用する。

### 2.4 MCTS自己対戦の探索不足

修正前は自己対戦でも常に最大訪問回数の行動を選び、同じ局面から同じ行動へ収束しやすかった。

修正後は次を導入した。

- 根ノードpriorへのDirichlet noise
- 序盤20ターンの訪問分布からの温度付きサンプリング
- それ以降と評価時は決定的な最大確率選択

ノイズは自己対戦時だけで、評価・本番推論には入れない。

### 2.5 複数選択の先頭64件偏重

複数選択の組み合わせが64件を超える場合、修正前は辞書順の先頭64件だけを使用していた。
後方indexを含む合法手がモデルから恒常的に見えず、MCTSとPPOの両方に影響していた。

修正後は全組み合わせのrank空間から64点を等間隔に選ぶ。全列挙せずにrankから組み合わせを
復元するため、組み合わせ爆発を避けながら入力全域をカバーし、同一局面では決定的な行動集合を返す。

### 2.6 MCTSゲーティングによる弱い候補の採用

修正前はcurrent bestと過去モデルへの勝利数を合算していた。このため実ログ上、
current bestへ3勝7敗の候補が、過去モデルを含めた16勝14敗で採用されていた。

修正後は次の両方を必須にした。

- current bestへの直接勝率が50%を超える
- 過去モデルを含む全体勝率も50%を超える

評価試合数も32へ増やした。各デッキ組を席交換し、さらにモデルへのデッキ割当も交換する4試合ブロックにした。generalistのゲーティング相手間では同じ固定matchup集合とPython seedを再利用するため、従来の「相手ごと・試合ごとにデッキ再抽選」より比較分散が小さい。CG native engine内部はseed指定できないため、shuffleまで同一という意味ではない。

### 2.7 MCTSのAdam状態リセット

修正前はラウンドごとにAdamを新規生成し、モーメント推定を失っていた。
修正後は採用中のネットワークとoptimizerを一体として管理する。

- 候補ネットワークへbest optimizerの状態を複製
- 候補採用時だけoptimizerも昇格
- 各ラウンドでネットワークとは別にoptimizer状態を保存
- クラッシュ再開時にoptimizerファイルがあれば復元
- 過去チェックポイントにoptimizerがなくても新規Adamで読み込める

ネットワークの`state_dict`形式は変更していないため、既存重みとの互換性は維持される。

### 2.8 PPOの更新幅監視

PPOは`approx_kl`を計算していたが、更新停止には使っていなかった。
修正後はエポック平均KLが0.02を超えた場合、残りのPPOエポックを打ち切る。
収集方策から急激に離れて学習が不安定になることを防ぐ。

## 3. 問題が見つからなかった箇所

PPOの以下の処理は妥当だった。

- 方策分布からの行動サンプリング
- behavior policyのlog確率保存
- 座席ごとに分離したGAE計算
- ラウンド全体でのadvantage正規化
- PPO clipping、entropy、勾配クリッピング
- optimizerのラウンド間維持と再開時復元

評価では先攻・後攻を1試合ごとに交換しており、座席偏りへの基本的な対策も入っていた。

## 4. 補足と保留事項

### 価値教師のブレンド

MCTSでは終局結果と探索時の価値推定を混合している。初期モデルの誤推定を教師へ戻す危険はあるが、
公式サンプルと同じ設計であり、現時点で変更効果を裏付ける比較実験がないため今回は変更していない。
終局結果のみ、固定混合、学習進捗に応じた混合をA/B比較すべきである。

### MCTSリプレイバッファとcheckpoint poolの復元（実装済み）

MCTSは直近ラウンドのSampleを`output_dir/replay`へラウンド別保存し、replay索引とarenaのcheckpoint poolを`checkpoints/training_state.pt`へatomic replaceで保存する。再開時はネットワーク、optimizer、replay、poolを同じ完了ラウンドから復元する。重みファイルだけが先に残る途中クラッシュでは、最後の整合ラウンドへ戻してやり直す。旧runに`training_state.pt`が無い場合は、後方互換として重み/optimizerを復元し、replay/poolだけ空で開始する。

### random相手評価

random相手にもラウンド内で固定したmatchup、Python seed、席・デッキ交換を適用した。ただし相手方策そのものが弱い点は変わらない。

random相手は疎通確認・下限確認としては有効だが、既に勝率が飽和しているためモデル選択には弱い。
固定デッキ群、固定seed、強いルールベース、過去bestを組み合わせた別評価スイートが必要である。

## 5. テスト

追加した回帰テストは次を確認する。

- 公開済みカードが自分の隠れ山札へ再出現しない
- 相手の仮定フルデッキが実在候補そのものである
- 山札・手札・サイド枚数がObservationと一致する
- 64件制限後も先頭・末尾indexを含む合法手が残る
- current bestへ負けた候補は、pool全体で勝っても採用されない

対象: `tests/test_mcts_quality.py`, `tests/test_fixed_evaluation.py`, `tests/test_mcts_training_state.py`, `tests/test_worker_event_log.py`
